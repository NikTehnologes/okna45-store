# Почему GIF уменьшился с 509 КиБ до 16,3 КиБ

Историческое сравнение, выполненное **до исключения `_ORIG` пользователем**: `LoadAnimation_ORIG.gif` и `LoadAnimation.gif`, GIF89a 320×240, не изменялись. `_ORIG` теперь не используется/не читается для сборки или повторной проверки. Источник ОС только выбранный `LoadAnimation.gif`. Настройки сайта-encoder неизвестны; выводы ниже сохранены из уже полученных measurements.

## Что поменялось

| Свойство | Оригинал | Оптимизированный GIF |
|---|---:|---:|
| Размер файла | **521335 байт** (509,1 КиБ) | **16658 байт** (16,3 КиБ) |
| Записанных image-кадров | **97** | **96** |
| Время одного цикла | **1940 мс** | **1940 мс** |
| Задержки | 97 × 20 мс | 95 × 20 мс + 1 × 40 мс |
| Полных image-кадров 320×240 | **97** | **1** |
| Площадь всех закодированных frame rectangles | **7449600 pixels** | **221139 pixels** |
| Кадров с прозрачностью | **0** | **95** |
| Disposal method | 2 — очистить область после кадра | 1 — оставить прошлую картинку |
| Кадров с отдельной локальной палитрой | **89** | **6** |
| Суммарные bytes таблиц цветов | **69120** | **2112** |
| Суммарные bytes LZW image data | **448355** | **12412** |

Размер уменьшился **примерно в 31,3 раза**, на **96,8%**. Формат не менялся: поддержка частичных image rectangles, transparent palette index и LZW — штатные возможности GIF.

1. **Повторяющийся фон не пишется заново.** В оригинале каждый image descriptor покрывает все 320×240. Оптимизированный GIF сохраняет первый полный экран, а далее только изменяемые прямоугольники: преимущественно узкая область ползунка.
2. **Прозрачность внутри прямоугольника** означает «оставить прежний pixel». Таким образом даже фон внутри bounding box не обязательно описывается новыми цветными pixels.
3. **Disposal 1 вместо 2** разрешает поверх предыдущей картинки рисовать фрагмент. Оригинал велел очищать кадр и потому требовал полного восстановления экрана.
4. **Палитры переиспользуются/сокращаются.** До оптимизации одни только global/local color tables занимали больше четырёх размеров всего маленького GIF. После оптимизации — 2112 bytes.
5. **LZW работает с меньшим и более повторяющимся потоком индексов.** Сам LZW был и в оригинале; выигрыш не от смены контейнера/«нового формата», а главным образом от того, какие данные encoder ему подал.
6. **Количество image records уменьшилось, timeline — нет.** Вместо двух 20-ms записей в одном месте используется одна 40-ms. Это не ускоряет анимацию: цикл всё ещё 1,94 с.

## Важная поправка: не полностью без потерь

Сравнение **раскрытых полных RGB-экранов на одной и той же временной шкале** показало различия во всех 97 исходных 20-ms интервалах. В худшем интервале изменены **627 из 76800 pixels (~0,82%)**; наибольшая разница одного R/G/B-канала — **13 из 255**.

Это не просто cropping прозрачного ползунка: есть небольшое изменение цветов/палитр. Причину конкретного encoder (lossy-настройка, re-quantization или palette remapping) нельзя назвать достоверно без сайта и его параметров. Сам факт pixel differences установлен, поэтому «не меняя формат GIF» верно, а «совершенно не меняя картинку» — нет.

Скриншот `Пример.png` не является animation source. Для ОС сохраняются все 96 frames/задержки **выбранного LoadAnimation.gif**. `_ORIG` пользователь убрал; его наличие в проекте не предполагается. **Пять циклов = 9700 мс**, не 5 секунд.

## Почему нельзя просто пропускать delta-записи GIF

Delta frame предполагает правильно восстановленный предыдущий экран. Если декодировать лишь выбранный image record после пропуска промежуточных, останутся старые pixels/«хвосты». Чтобы выбирать текущий кадр по времени без queue/catch-up, Pico-доставка должна содержать **адресуемое полное состояние небольших изменяемых областей** либо ключевые состояния, а не требовать применения всех пропущенных delta по цепочке. Полный framebuffer 153600 bytes и набор распакованных кадров в RAM для этого не нужны.
